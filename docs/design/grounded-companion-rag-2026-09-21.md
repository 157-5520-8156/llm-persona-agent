## 结论

把事实虚构作为 RAG 问题分析是有用的：先判断有无足够证据，再区分索引、检索、
读取和生成失败。此前不断修来源接口和生成后的审核，尚未建立这些环节的成对对照，
不能据此认定检索已经足够，也不能继续把所有失败都归因于模型不遵守规则。

本项目适合复用现有结构，明确三条路径：**当前状态直接读取；历史经历与前史检索；
新事件由具有相应权限的角色／World 路径产生并落账。** 检索和审核都不能代替生活本身。

## 业内做法及适用边界

| 来源 | 主要依据 | 对本项目的意义 |
| --- | --- | --- |
| [Google：Sufficient Context](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/) | 区分上下文不足与证据充分时的生成失败；提供检索内容并不保证正确使用 | 每个失败先标注是否可由已有证据回答，避免混着修 |
| [Microsoft：RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators) | 分开评价检索质量、回答依据、相关性和完整性 | 同时统计能否回答、是否说对；拦截或没有回复不能当作体验成功 |
| [Anthropic：Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 为片段补上下文，结合词法与语义检索，按效果选择重排 | 优先检查主体／时间信息是否在索引中保留，以及实际召回；生成的索引提示不能获得新的事实权限 |
| [LongMemEval](https://arxiv.org/html/2410.10813v2) | 拆分索引、检索、读取，测试时间推理、知识更新、未知问题；用正确证据输入辅助定位 | 对照正常检索与人工选定的原始证据；摘要／事实可增强索引，不应替代全部原记录 |
| [Generative Agents](https://arxiv.org/html/2304.03442v2) | 区分观察、反思和计划，检索考虑相关性、近因及重要性；反思有证据指针 | 生活事件、个人解释和未来计划需保持不同语义；其短期实验仍出现虚构，不能当长期可靠性保证 |

以上包括工程指南和研究方案，不存在已经保证“陪伴角色永不虚构”的统一行业标准。
例如 Contextual Retrieval 的改善衡量的是检索失败率，不能直接换算为本项目幻觉降低比例。

另两条适用的工程经验：

- [LangGraph 官方记忆概念](https://docs.langchain.com/oss/python/concepts/memory)区分当前执行状态与长期记忆，记忆更新还涉及即时性和延迟的取舍。这里采用这个区分即可，无需迁移框架。
- [Microsoft Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)以已接受事件生成可查询的当前视图。本项目已有 ledger／projection，可复用；无需另起状态数据库。**工程推论**：仅对有初始值且变更链完整的字段，才能维持“直到变更前仍有效”；没有初始化或没有完整记录的字段必须保持未知。

## 已有能力与需要实测的缺口

- `recall_corpus.py` 已收集对话、Fact、Experience、World life 和 Memory，保留来源；
  文档上限 256，且会截断正文，不直接收集完整活动生命周期历史。需要测遗漏发生在哪一层。
- `recall_index.py` 已有词法、向量、结构关联和时间混合评分，也有主体、隐私、状态、
  有效期过滤及来源多样性重排。不能把建议写成“从零加一个向量库”。
- `run_world_v2_longitudinal_audit.py` 的宿主构建显式设置
  `use_configured_recall_embedding=False`；本地默认向量为 `feature-hash-ngram.1`。
  09 的 `manifest.json` 明记 `semantic embedding disabled`，实际库中索引版本为
  `world-v2-recall-index.hybrid.7+embedding:feature-hash-ngram.1`。
  因此这轮验证的是本地混合检索，向量通道使用词面特征哈希，不能当作远程语义召回
  已经生效的证据。这值得补测，但无法解释本就不存在的身体状态。
- 最近首稿约 3.6 万输入 tokens，说明上下文需要测量与筛选，尚不证明长度是根因。
  [Anthropic 的上下文工程指南](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
  建议提供足够且高信号的上下文；这里应保留完整来源绑定，在实验中减少无关材料，
  而不是继续累加提示词或删除事实权限。

## 下一步：先做小型分层对照，再选一个修复

1. 固定首批 12 个有来源的场景，覆盖真实经历、前史、用户／角色主体、状态更新、
   计划与实际结果、未知与纯主观表达。规模是本项目的工程取舍；先从已有日志和 fixture
   取样，标注可回答范围、原始记录和时间，人工核对后才运行模型。
2. 对可回答问题比较两种输入：现有正常检索；人工选定充分的**原始证据**。
   保持角色、模型、问题、事实版本和允许行为一致。后者也可能减少干扰材料、缩短上下文，
   首轮改善只能说明整套输入更有效。进一步的检索对照固定呈现方式和预算，核对证据覆盖
   差异；组织对照固定同一组证据及其权限，仅改变排列或编码。相同 token 预算本身不足以
   隔离原因，不能把首轮改善直接归功于某个检索算法。
   无依据场景保留未知，不能在对照中发明“正确经历”。
3. 离线先测候选覆盖率、筛选／截断原因、召回率及主体／时间正确性；真实模型阶段
   再记受支持回答、无依据补写、审核误拒、有效回复率、延迟、tokens 和实际累计费用。
   角色自主选择沉默与技术未交付分别统计；安全但始终不回复不能算通过。
4. 根据结果只改定位到的一层：证据缺失修初始化／既有事件落账；检索漏失修索引与排序；
   充分证据仍出错修上下文和生成接口；误杀修审核判定。先修有复现与正反对照的一项，
   不同时更换模型、检索器和审核，以免再次无法归因。
5. 小集改善后再回同一身份的连续聊天，最终候选冻结再做发布回归。小集不能证明一周
   不重复或人格长期稳定；已有长期旅程验收继续保留。本轮尚未创建或运行这批对照。

实现时维持角色权限：她可以选择此刻的感受、意图和新的行动；行动结果依现有权限路径
落账后才成为经历。角色前史由明确的创作／审核流程进入档案，再与后天记忆互通；
对话中不临时补造既定过去。未知信息的表达由角色选择，不加固定“我不知道”话术。

今后的疑难问题采用同一方法：先查可靠资料，写可区分的假设，用最小实验取证，
再作局部改动。没有新证据时停止重复同样的付费试聊或继续堆规则。
