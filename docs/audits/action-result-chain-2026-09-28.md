# 行动结果到聊天：接线检查与修复

2026-09-28。结论：不能把聊天看不到经历一概归因为事件机没有生成。本轮定位并修复了**检索候选受展示预算裁剪**、**检索生活结果未进入来源审核**两处缺陷。生产未重启、未向QQ发送；所有真实对话均为独立SQLite副本与CaptureDelivery。

## 原假设的纠正

上一轮在作者输入/审核来源表里没有找到 `authorized_attempt_result`，只证明本轮可见来源缺失，不能证明数据库中不存在。使用同一个历史验收账本 `release-repair-20260928/smoke/clone.sqlite` 的独立副本检查后，发现其中已经保存3条照片进度结果，均有结算和内容记录，例如“一部分照片被挑出归类，当天记录只写下零散几句，归档仍未完成”。这些结果位于9条结算与9份经历内容之中。它们属于此前隔离验收世界，不是对当前真实生产状态的最新统计。

更早的v4 World Author样例确实曾把结果写成“时间窗不证明到场/完成”的规则说明；之前v5已增加有限结果生成权限。但本轮这个可复现缺口发生在下游，不能再次归咎于事件机。

## 改动

1. `LifeContentCompiler.compile(budget=None)`供本地检索语料构建读取原有可读材料，保留原来的游标、参与者、隐私、撤回/限制、哈希及结算校验。聊天展示默认480字/条、1440字总预算不变。
2. `LedgerProjectionContextResolver`给Recall独立的生活来源和可读经历关联记忆集合，不再使用展示窗口决定候选资格。查询结果的数量、字节预算保持原限制；BGE-M3未更换，未增加LLM调用步骤。
3. 生活检索文档保留有界的原结算材料及确切事件来源。新的index reading `.10`将环境与已授权尝试结果显示给作者；`.9`及更早的读取形状保持原语义。来源材料通过延迟解析的JSON字段携带，避免Recall审核类型与World投影类型之间的导入循环；解析后仍按原WorldLife类型严格校验。
4. 只有经过验证且确实展示给获胜作者的生活检索结果，才补入来源表。检索排序文字、未展示结果、其他角色、未结算候选、错游标/哈希、withhold材料均不获得权限。主体、结算、描述记录与原字段仍须匹配。
5. 新读取版本在比较实际展示内容前还原该请求认证的短编号；绑定描述记录的真实事件类型 `LifeContentRecorded`，不把搜索侧旧标签当实际事件名。作者可引用的来源与审核器的来源保持一致。
