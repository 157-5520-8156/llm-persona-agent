## 确认的问题

1. **审核丢失日常语言的语境。** 第一轮“被那片叶子盖了个章”被两份无用户上下文的
   语义读取展开成真实叶子接触事件，来源审核也沿用该解释。纠正稿“别搓了，再搓手该红了”
   又因没有此刻正在搓手的记录被拒。第三轮“那就不给建议”被要求证明此前存在给建议的
   语境，尽管当前用户消息已明确说不想要建议。
2. **指代与时间误读会进入硬权限判断。** 第三轮“手上有蓝，今天画那片叶子不算什么都没
   干成吧”被错归为角色自己沾蓝、画叶子；“我在这儿”一度被要求提供实际位置证据。
   第二轮纠正的最后阻断，则是把用户当前报告“懒得洗”读成 `past_subjective_state` 后
   被来源权限拒绝。不能用降低权限要求来补偿错误语义。
3. **作者确实仍会补出缺乏依据的生活经历。** 第二轮初稿说“刚在校园路上走了一段”；
   第三轮原本没有生活经历的稿子，在纠正后变成“刚在校园路上走了一段，风把叶子吹得到处
   都是”。活动状态不证明已完成行走，已有环境也不支持后半句。此类拒绝有依据，不能和
   玩笑、指代的误拒一并放开。第二轮纠正的来源模型曾把 active 活动当作进行中行走的支持，
   同样显示审核不只是偏严，还存在权限理解不一致。
4. **修正流程会增加成本，却不保证更可靠。** 一条普通消息进入生成、两份语义读取、来源
   审核和纠正后复核，三次均未交付。仅缩短作者 system 没有解决完整流程的问题；第三轮
   还出现纠正稿引入原稿没有的生活断言。

v22 并非在代码层强制读者命题成立：来源审核已有 `not_record_bound` 通道，也已有
推翻读法的离线覆盖。但语义读取只拿完整 Beats，没有本轮用户原文；下游在本次实测中
没有可靠地纠正比喻、省略主语和时态误读。固定 fact_id 不应被误当作正确命题的证明。
后续修复应让已有、绑定的用户原文参与语言消歧，保留完整原句检查和真实事件的证据权限。
旧审核请求及回执按版本恢复，不应直接改共享提示词破坏已有证据。此处记录修复方向，
**本轮没有修改生产逻辑，也没有验证该方向的模型效果**。
