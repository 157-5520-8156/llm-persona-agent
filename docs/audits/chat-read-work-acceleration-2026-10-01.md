# 聊天读取加速：同内容对照与实际回复时间

2026-10-01，基线 7c402572。用户要求在保持质量的前提下压缩回复时间。
仅使用同一冻结生产副本和 CaptureDelivery，未给 QQ 发消息或切换生产。

## 归因与修改

新三轮基线首条捕获约 8.44/6.99/8.14 秒。采样计时显示上下文阶段
约 1.8–2.7 秒；阶段日志是累计时间，model_ms 不能再与 context_ms 相加。
真实远程角色请求本身约 2–3 秒，准备、检索、输出接受和发送也占时间。

本轮只减少重复工作：

- 有限 LRU 缓存不可变 proposal/audit、WorldConsequence 与 Experience 摘要的纯解析。
  当前来源是否存在、主体、版本、权限、描述符和正文哈希仍重新检查；不缓存权限成功结果。
- RecentDialogue 先按当前候选 action 查询回执，再验证实际 owning commit。
  SQLite partial expression index 避免扫描整份事件 JSON；强制使用已安装的专用查询计划。
  全部相关回执状态和最早可见回执保持，内存账本保留原路径。

初次无专用索引的查询更慢，未选用；仅保留完成索引与查询计划验证后的实现。
参考 [SQLite JSON](https://www.sqlite.org/json1.html)，使用既有存储形态，不迁移事件到 JSONB。

## 无模型的同内容对照

同一冻结快照、相同 actor/scope/cursor/query，交替启用原工作与新工作。
四次完整 model_content_json **字节一致**，没有删除记忆、世界信息或引用。

| 条件 | 两次上下文编译时间 |
|---|---|
| 原工作 | 0.879 / 0.803 秒 |
| 优化 | 0.673 / 0.704 秒 |

平均节省约 0.15 秒（约 18% 的这一段），不是整轮回复提速 18%。
近期对话编译的 indexed/fallback 原始结果也逐项相同。

## 实际聊天

最终候选未开启 cProfile 时，三轮首条捕获为：

| 问题 | 首条文字捕获 | 作者路径 |
|---|---:|---|
| 今天过得怎么样 | 6.34 秒 | 单次角色作者调用 |
| 小时候生日最记住什么 | 9.28 秒 | 角色主动 Recall，增加一次作者调用 |
| 想找许桥帮忙会犹豫吗 | 5.81 秒 | 单次角色作者调用 |

另有本地文本终点预测，不能将 HTTP 请求数全算成角色作者次数。
最终三轮均 action_authorized 并有本地捕获。生日中的塌蛋糕、拍照、父亲找打火机、
蜡烛意外吹灭等细节回查实际 family-f09 原文有据。
许桥轮角色选择先问用户怎么知道这个名字，没有回答犹豫本身；这是角色选择，
不能将其当成短而完整回答的质量提升。

带 cProfile 的基线与候选不能直接计算总提速；输入会随前轮真实措辞改变，
LLM 输出长度、Recall 和缓存也有波动。这里**没有稳定 <5 秒或 P95 合格证据**。
必要 Recall 没有被禁止或减频，角色数据没有因为速度目标缩减。

## 验证与剩余项

415 项 SQLite/上下文/生活感受/记忆/检索/角色协议检查通过，Ruff、diff check 通过。
专门验证缓存预热后删除描述符或世界来源仍拒绝读取，以及回执查询使用专用索引。
本轮没有完成全套发布门禁、长期质量、每日成本或真实 QQ 到达延迟验收。

剩余关键路径主要是首轮准备、语义预取未及时完成造成的额外作者回合、
模型请求/输出和接受后的处理。下一步应针对这些阶段取样，不能以关闭必要检索、
跳过来源检查或固定角色话术换取速度。
